## 1. Decision log

### D001 — 使用 SwiftUI + AppKit，不用 Flutter

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：只做 macOS；需要 PDFKit、Quick Actions、列印、沙盒整合。
- **決策**：SwiftUI 為主，AppKit bridge 處理 PDFView/NSDocument。
- **理由**：原生、較小、較快、較好整合；不需要跨平台。
- **替代方案**：Flutter（RevPDF 路線）— 前期跨平台，但 macOS 整合與 PDFKit 仍需 native plugin，複雜度更高。
- **後果**：未來若要 Windows/iOS，需另寫或重構。

### D002 — 第一版用 PDFKit，不引入 PDFium

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：需要渲染、註解、表單、搜尋、列印、頁面操作。
- **決策**：PDFKit + CoreGraphics 為核心；PDFium 列為未來選項。
- **理由**：PDFKit 涵蓋 80% 功能；PDFium 需自編 XCFramework、C++ 介面、簽章、記憶體管理。
- **替代方案**：一開始就用 PDFium — 功能更底層，但開發/維護成本高。
- **後果**：真文字編輯與 content stream 塗黑需另建或導入 PDFium。

### D003 — 使用 NSDocument，不用 DocumentGroup

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：需要多視窗、最近文件、自動儲存、版本、檔案協調。
- **決策**：`NSDocument` + SwiftUI window content。
- **理由**：成熟、可控、與 AppKit 整合好。
- **替代方案**：`DocumentGroup` — 較新，但自訂儲存/恢復/多視窗控制較少。
- **後果**：需要寫一些 AppKit bridge。

### D004 — 塗黑 v1 用 rasterize

- **狀態**：Accepted（待使用者確認）
- **日期**：2026-11-02
- **背景**：PDFKit 不支援 content stream 編輯；畫黑框不安全。
- **決策**：v1 將受影響頁面 300 DPI 點陣化、蓋黑、替換頁面、清理 metadata。
- **理由**：保證看不到；實作簡單；可驗證。
- **替代方案**：CGPDFScanner（保留向量，但難度高）；PDFium（需依賴）。
- **後果**：失去文字/向量、檔案變大；v2 再改 content stream。

### D005 — 不做帳號、雲端、協作

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：目標使用者在意隱私；內部使用不需要協作。
- **決策**：全部本機；沒有登入、沒有上傳、沒有同步。
- **理由**：產品原則 local-first；降低複雜度與法規風險。
- **替代方案**：雲端同步/協作 — 功能更強，但偏離定位。
- **後果**：無法跨裝置同步；使用者需自行備份。

### D006 — GitHub repo 不附 LICENSE

- **狀態**：Accepted（使用者指定）
- **日期**：2026-11-02
- **背景**：使用者要求在 GitHub 開 public repo，no license。
- **決策**：不建立 LICENSE 檔；README 說明「No license granted」。
- **理由**：尊重使用者要求。
- **後果**：法律上預設保留所有權利；這是 source-available，不是 OSI open source。若未來要開源，需另加 license 與貢獻者條款。

### D007 — 第一版只做繁體中文＋英文

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：RevPDF 有 16 種語言；我們是內部使用。
- **決策**：zh-Hant + en；其他語言架構保留。
- **理由**：降低翻譯/測試成本；先把主要語言做好。
- **替代方案**：跟 RevPDF 一樣 16 種 — 成本高，品質難保證。
- **後果**：非中英文使用者需等待。

### D008 — 第一版目標 M2，完整版 M3

- **狀態**：Proposed（待使用者確認）
- **日期**：2026-11-02
- **背景**：M3 包含塗黑/比對/Flows，工作量較大。
- **決策**：先做 M0–M2 可用版本，再決定 M3。
- **理由**：早點 dogfood，降低風險。
- **替代方案**：直接衝 M3 — 時間長、回饋晚。
- **後果**：M3 功能延後。

### D009 — 不做 IAP、廣告、訂閱

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：内部使用；RevPDF 的 Premium 對我們無意義。
- **決策**：沒有金流、沒有廣告、沒有試用倒數。
- **理由**：降低複雜度；維持 no dark patterns。
- **後果**：若未來對外，需另設計商業模式。

### D010 — 第一版不做自動更新

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：內部使用；更新頻率可控。
- **決策**：手動換版；未來可加 Sparkle。
- **理由**：減少攻擊面與簽章/更新基礎設施。
- **後果**：使用者需手動下載新版本。

### D011 — 第一版零第三方 runtime 依賴

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：降低供應鏈風險與建置複雜度。
- **決策**：只用 Apple frameworks；PDFium/Sparkle/SDK 都是未來選項。
- **理由**：安全、可維護、App 較小。
- **後果**：某些功能需自建或延後。

### D012 — Repo／產品名稱：MacPDF

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：需要一個不與 RevPDF 混淆、可公開的名稱。
- **決策**：GitHub repo `MacPDF`，產品名稱「MacPDF」。
- **理由**：簡短、可辨識、清楚指向 macOS。
- **後果**：文件、bundle 範例與 CLI 統一使用 MacPDF。

### D013 — 最低 macOS 14

- **狀態**：Proposed
- **日期**：2026-11-02
- **背景**：需要 PDFKit/Vision 新 API；使用者機器是 macOS 27。
- **決策**：macOS 14 Sonoma 以上。
- **理由**：覆蓋大多數現代 Mac；避免支援過舊 API。
- **替代方案**：macOS 13 — 覆蓋更廣，但部分 API 需 fallback。
- **後果**：舊機無法使用。

### D014 — 不執行 PDF JavaScript

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：安全風險；PDFKit 預設不執行。
- **決策**：不執行 JS；匯入時偵測；清理時移除。
- **理由**：降低攻擊面。
- **後果**：部分互動式表單可能不正常。

### D015 — 第一版不做 PDF→Office

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：版面重建難度高、品質難保證。
- **決策**：先做 PDF→文字/RTF；DOCX/XLSX 列 M4。
- **理由**：避免「看起來可以、實際排版壞掉」。
- **後果**：需要 Office 輸出的使用者需另找工具。

### D016 — 第一版不做真文字編輯

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：PDF 無段落模型；需要 content stream/字型/reflow/表格。
- **決策**：先做文字方塊/圖片/註解；真文字編輯列 M4。
- **理由**：成本遠高於其他功能。
- **後果**：與 RevPDF 的功能差距主要在這一塊。

### D017 — Sandbox 開啟

- **狀態**：Proposed
- **日期**：2026-11-02
- **背景**：內部使用可關沙盒簡化檔案存取，但未來可能對外。
- **決策**：開 sandbox + security-scoped bookmarks。
- **理由**：安全、未來可上架、养成好習慣。
- **替代方案**：關 sandbox — 開發快，但風險高。
- **後果**：最近文件/檔案存取需 bookmark 處理。

### D018 — 內部使用 ad-hoc 簽章

- **狀態**：Proposed
- **日期**：2026-11-02
- **背景**：不需要上架。
- **決策**：Development/ad-hoc 簽章；對外時再 Developer ID + 公證。
- **理由**：降低初期成本。
- **後果**：其他 Mac 可能需手動允許。

### D019 — Google Fonts 列為選用

- **狀態**：Proposed
- **日期**：2026-11-02
- **背景**：RevPDF 可下載 Google Fonts；我們強調離線。
- **決策**：預設只用系統字型；Google Fonts 下載列 P2，可關閉。
- **理由**：維持零網路預設。
- **後果**：字型選擇較少。

### D020 — 不做手機 App QR/跨裝置推廣

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：RevPDF 有「用手機掃 QR 開 App」的推廣。
- **決策**：不做。
- **理由**：我們只做 macOS；沒有手機版。
- **後果**：少一個成長管道（目前也不需要）。

### D021 — PDF/A-2a 不列第一版；先做 2b

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：官網把 PDF/A-2a 列為 5.0 功能。2a 需要 tagged PDF、structure tree、Alt text、Lang、Unicode mapping。
- **決策**：M2/M3 先做 PDF/A-1b/2b/3b；2a 列 G18（P2/M4），優先評估商業 SDK。
- **理由**：PDFKit/CoreGraphics 不提供建立 structure tree 的高階 API；自建 tagging 成本極高。
- **後果**：短期內不宣稱支援 2a；若需要，走 SDK 或專案。

### D022 — Compare 與 Flows 優先於 Excel/Word

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：四個旗艦功能中，Compare/Flows 技術較可控、使用頻率高。
- **決策**：M3 先做 Compare 與 Flows；Excel/Word 放 M4。
- **理由**：投報率高、風險低；Excel/Word 的版面重建品質難保證。
- **後果**：M3 的功能組合以「審閱 + 自動化」為主。

### D023 — Excel/Word 先做簡單文件，不承諾複雜版面

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：官網強調 PDF→Excel/Word 的輸出品質。
- **決策**：先支援簡單表格/段落；複雜多欄、合併儲存格、掃描件標示為限制。
- **理由**：避免「看起來可以、實際排版壞掉」。
- **後果**：需要高保真時，評估商業 SDK。

### D024 — 壓縮分階段：先影像取樣，再物件級重寫

- **狀態**：Accepted
- **日期**：2026-11-02
- **背景**：官網說「更小的檔案、更好的品質控制」。
- **決策**：M2 做 C1（rasterize/影像取樣）；M3 做 C2（image XObject 重寫）；C3/C4 再評估。
- **理由**：C1 簡單但失去文字；C2 保留文字/向量但工程量大。
- **後果**：第一版壓縮可能以畫質換大小；物件級壓縮延後。

## 3. Decision process

- 每個影響架構/範圍的決策，開一個 GitHub Issue，標籤 `decision`。
- 決策文件格式：背景、選項、決定、理由、後果。
- 決策一旦 accepted，更新本文件與相關規格。
- 若決策變更，保留舊記錄，不要直接覆寫；標記 superseded。

## 4. Assumptions to revisit

- 使用者主要用 Apple Silicon；Intel 測試可能不足。
- PDFKit 足以支撐 M0–M3；若不足，需重新評估 PDFium。
- Vision OCR 對繁中/英文夠用；若不夠，需 Tesseract/其他方案。
- 內部使用者願意接受 rasterize 塗黑的畫質損失。
- 不需要雲端/協作。
- 不需要 PDF JavaScript。
